# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Native SwiftUI macOS app (deployment target **macOS 27.0**, Apple silicon / `arm64` only, **Swift 6 language mode**) for live NZ Transport Agency traffic cameras, road events, VMS signs, and travel times. No package manager, no analytics, no backend — just `swiftc` against the macOS SDK plus an Xcode project that points at the same sources. Model-layer unit tests run via `./run_tests.sh` (a standalone swiftc executable, no SwiftPM/XCTest). Don't add `#available` / `@available` gates for anything macOS 27 already has.

## Build / run

Two parallel build paths exist; both must keep working:

- **Xcode**: `NZTraffic.xcodeproj` (objectVersion 77), shared scheme `NZ Traffic`. `Sources/` is a **file-system synchronized folder** attached to the app target, so any `.swift` file dropped into `Sources/` (flat, matching `build_app.sh`'s `Sources/*.swift` glob) joins the build automatically — no pbxproj edit needed. Keep non-source files out of `Sources/` (a synchronized folder would bundle them as resources). `Resources/Info.plist` and the Icon Composer icon `Resources/AppIcon.icon` (built as the target's `ASSETCATALOG_COMPILER_APPICON_NAME = AppIcon`) are explicit references; `Tests/` is a synchronized folder with **no** target membership (navigator only), and `CLAUDE.md` / `README.md` / the scripts are navigator-only file references.
- **Shell**: `./build_app.sh` — invokes `swiftc` directly (no SwiftPM), produces `build/NZ Traffic.app` plus a matching `build/NZ Traffic.app.dSYM`, compiling `Resources/AppIcon.icon` with `xcrun actool` (→ `Assets.car` + `AppIcon.icns`, and a partial plist whose `CFBundleIconName` / `CFBundleIconFile` are merged into the bundle's Info.plist — the source Info.plist sets neither, as with Xcode). `arm64` only by default; `ARCHS` still takes a space-separated list (e.g. `ARCHS="arm64 x86_64"` for a lipo'd universal binary + merged dSYM). `MACOSX_DEPLOYMENT_TARGET` overrides the min OS (default `27.0`) and is also stamped into the bundled Info.plist's `LSMinimumSystemVersion`, so the Mach-O `minos` and the plist always agree.

The two paths are kept equivalent to the Xcode Release configuration: Swift 6 language mode + `MemberImportVisibility` upcoming feature, `-O` with whole-module optimisation, debug info → dSYM, dead-code stripping, deployment target 27.0, `arm64`, and an ad-hoc signature **with the hardened runtime** (`codesign --options runtime --sign -`). Remaining differences: Xcode's Info.plist processing adds the `DT*` / `BuildMachineOSBuild` / `CFBundleSupportedPlatforms` keys and uses explicit module builds; the DMG still packages the `build_app.sh` output. Neither path is notarized (ad-hoc signatures can't be) — distribution is ad-hoc signed DMGs on GitHub Releases. If you change a compiler flag or deployment setting, change it in `build_app.sh`, `run_tests.sh` **and** the pbxproj.

Concurrency settings are deliberate: Swift 6 strict checking is on, but **Approachable Concurrency is off** (`SWIFT_APPROACHABLE_CONCURRENCY = NO`) and default actor isolation stays `nonisolated` (no `SWIFT_DEFAULT_ACTOR_ISOLATION`). The async entry points in `TrafficAPIService` are `@concurrent` so decoding stays off the main actor even if that changes; keep new async fetch/decode helpers `@concurrent` too.

CLI release build:

```sh
xcodebuild -project NZTraffic.xcodeproj -scheme "NZ Traffic" -configuration Release -destination 'generic/platform=macOS' build
```

`./package_dmg.sh` rebuilds via `build_app.sh`, stages with an `Applications` symlink, checks the staged signature (including the hardened-runtime flag), and emits `dist/NZ-Traffic-<version>-macOS-arm64.dmg` (the arch label comes from the built binary; a universal override is labelled `universal`) plus a matching `…dSYM.zip` for symbolicating crash reports. `Resources/Info.plist` is the **single source of truth** for `CFBundleShortVersionString` and `CFBundleVersion` — bump both there. The pbxproj deliberately has no `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION`, so editing the version in Xcode's General tab is not the way to do it.

Run the built app: `open "build/NZ Traffic.app"`.

### Tests

`./run_tests.sh` compiles the Foundation-level sources — `Models.swift`, `AppIdentity.swift`, `RefreshPolicy.swift`, `OfflineCache.swift`, `TrafficAPIService.swift`, `TrafficStore.swift`, `ViewLogic.swift`, `MapClustering.swift` and `Watchlist.swift` — plus `Tests/*.swift` into a standalone executable and runs it (exits non-zero on failure) with `CFFIXED_USER_HOME` pointed at `build/test-home`. It can be run from any directory, uses the same Swift 6 / `MemberImportVisibility` flags as the app, always builds for the host architecture (`ARCHS` is ignored; `TEST_ARCH` forces a slice), and prints each test group name to stderr so a trap is easy to locate. Tests cover the pure model logic (lossy decoders, coordinate validation, WKT parsing, VMS message formatting, NZ date parsing/formatting, `matches(region:highway:search:)`), the refresh policy (intervals, freshness banner, Dock badge, `SingleFlight`), the views' Foundation-only logic (map layers and clustering, line styles and pin glyphs, the congestion text list, the travel-time board list), the watchlist and closure-notification logic, and the API client, `OfflineCache` and `TrafficStore` end to end against `StubURLProtocol` (`Tests/StubNetwork.swift`: an in-process route table, no network), temporary cache folders and a `TestClock`. `Tests/Fixtures/` holds trimmed **verbatim** records from the live feeds (cameras, events, VMS, journeys, TIM, regions, EV GeoJSON, congestion XML — chosen for the edge-case shapes; `FixtureTests.swift` decodes them through the app's payload types, the API client and the store); add a record there, copied from a real response, when a new upstream shape needs covering, and keep the folder small. The suite runs three times — in the Mac's own time zone, `TZ=UTC` and `TZ=America/Los_Angeles` — so date code that forgets to pin NZ time fails even on a Mac set to NZ time. Top-level test code is async and main-actor, like the store. They deliberately avoid SwiftPM/XCTest and do **not** compile the SwiftUI/AppKit layer, so keep those nine files free of `SwiftUI`/`AppKit` imports (Foundation, CoreLocation, CryptoKit, Network, Observation and Synchronization are fine). Tests must never read or write the real user's defaults or Application Support — use pure in-memory seams (e.g. `DiagnosticsReport.collectPreferences(from: [String: Any])`, `diagnosticsReport(preferences:)`), `OfflineCache(directory:)` on a temporary folder, and `TrafficStore(service:cache:imageCache: nil, monitorsNetwork: false, reconnectDelay:clock:)` (retries without sleeping via `RetryPolicy(baseDelay: .zero)`; reachability driven by `networkStatusChanged(isOnline:)`). `Tests/` is not part of either app build path; new test files must be added to the `swiftc` invocation in `run_tests.sh`.

## Architecture

Swift files under `Sources/`, organized by layer not feature:

- `NZTrafficApp.swift` — `@main` entry: a single main `Window(id: SceneID.main)` (not a `WindowGroup` — reopening it from the menu bar, Dock or Window menu brings back the same window), a secondary `Window(id: "help")`, a `Settings` scene (`SettingsView`, ⌘,) and the `MenuBarExtra`; `NZTrafficCommands` replaces the About panel and Help menu items (Help, Export Diagnostics…, Clear Offline Cache…). `init()` installs a bounded shared `URLCache` (camera images), creates the store and `AppController` and starts it. `MenuBarContent`'s "Open NZ Traffic" is `openWindow(id: SceneID.main)` + `NSApp.activate()`.
- `AppController.swift` — window-independent services owned by the App: starts the store's launch load (bracketed by `LaunchGuard`), feeds `store.configureAutoRefresh` from the `nzta.*` defaults (observed via `UserDefaults.didChangeNotification` — the one path from the filter-bar menu, Settings and Welcome to the scheduler; also migrates a stored interval below 60 s), feeds `store.updateAppActivity` from app-activation / window-occlusion notifications, and sets the Dock badge from `store.dockBadgeLabel` (via `Observations`). It also loads the watchlist from `nzta.watchlist` into the store and saves it back when it changes (via `Observations`), and hands `store.onNewWatchedClosures` to `ClosureNotifier`. Also the `AppDelegate` whose `applicationShouldTerminateAfterLastWindowClosed` is `false`: closing the window must not quit the menu-bar app.
- `RefreshPolicy.swift` — Foundation-only refresh policy: `DataSection`, `AutoRefreshPolicy` (60–600 s interval, background back-off, next-tick delay, camera-image reload spacing, reconnect rule), `FreshnessBanner` (what the banner above each tab says), `DockBadge`, `LaunchGuard`, and the generic `SingleFlight` the store coalesces loads with.
- `OfflineCache.swift` — the `OfflineCache` actor and `ContentDigest` (SHA-256), Foundation-only (see the offline-cache exception below).
- `TrafficAPIService.swift` — thin `URLSession` wrapper over the NZTA traffic REST endpoints (`/cameras/all`, `/events/all/10`, `/signs/vms/all`, `/journeys/all/10`, `/signs/tim/all`, `/regions/all/10`) at the undocumented `https://trafficnz.info/service/traffic/rest/5`, plus the congestion XML and the ArcGIS EV feed. A 404/410 from rest/5 retries that path once on the documented rest/4 and remembers it for the session (`APIVersionFallback`, reported in diagnostics). The session fails fast (`waitsForConnectivity = false`, 30 s idle / 90 s resource timeout; journeys gets a 60 s request timeout because the server spends 14–17 s on it). `RetryPolicy` retries only transient failures (`isRetriable`: 5xx and transport errors other than unreachable-host / timeout / offline codes, which `.transport` keeps as `URLError.Code`); URLSession cancellation surfaces as `CancellationError`, never as a network error. Every fetch returns a `SectionFetch` (decoded value, raw bytes, `ContentDigest`, skipped-entry count) and has a `…Result()` variant (`@concurrent`, so decode always runs off the main actor) that converts throws to `Result` so the store can surface per-section errors without one failure killing the others.
- `TrafficStore.swift` — `@Observable @MainActor` class holding cameras / events / VMS / journeys / TIM / congestion / EV, per-section loading state and errors, `lastUpdated`, `imageCacheToken` / `cameraImageGeneration`, reachability (`isOnline`) and data provenance (`savedSections`, `failedSections`, `savedDates`, `lastLiveSuccess`) from which `freshnessBanner`, `eventsAreProvisional` and `dockBadgeLabel` derive. Owns loading (see Refresh model), the auto-refresh scheduler, the `OfflineCache` and an `NWPathMonitor`. `filtered*` results are memoized behind a `FilterKey` cache (`@ObservationIgnored`), cleared per section when that section's data changes. `TrafficStore(service:cache:imageCache:monitorsNetwork:reconnectDelay:clock:)` takes every dependency (`clock` is "now" for every time-dependent decision); `OfflineCache(directory: nil)` is a no-op cache.
- `Watchlist.swift` — Foundation-only (compiled by the test runner): `Watchlist` (watched highways as canonical highway keys, cameras and journeys by id; JSON in UserDefaults under `nzta.watchlist`; `watches(_:)` for cameras, events — by highway or the event's `journey.id` — and journeys), `WatchedClosureTracker` (the first successful live events fetch only records a baseline of every active closure; later fetches report active closures on watched roads not in the previous set, each once per session) and `closureNotificationContents` (one notification per closure, a single summary above three).
- `ClosureNotifications.swift` — `ClosureNotifier` posts those notifications with `UNUserNotificationCenter` while `nzta.notifyWatchedClosures` is on (off by default; Settings asks for permission only when it is first turned on) and is the notification centre's delegate: a click calls `AppNavigator.show(.events)`, which asks the main window for the Road Events tab and reopens it through the `openWindow` action ContentView / the menu bar handed over. The store finds new closures on its own refreshes, so this works with the window closed.
- `WatchControls.swift` — the watch UI: `WatchStarButton` (cameras, journeys), `watchContextMenu` (watch the item or its highways; also VoiceOver actions), `WatchedEventBadge`, the "Watching" filter chip and Settings' watchlist / notification sections. They read `TrafficStore` from the environment (ContentView provides it) and hide without one.
- `PreviewSupport.swift` — `#if DEBUG` only. `TrafficStore.preview()` returns a store whose `URLSession` is answered in-process by `PreviewURLProtocol` (small canned fixtures per endpoint, no image URLs) with a disabled `OfflineCache`, so `#Preview`s never hit the network or the user's real cache. Previews must use it rather than a live `TrafficStore()`.
- `Models.swift` — all decodable types plus payload wrappers (`CamerasPayload` → `CameraResponse` → `[TrafficCamera]`, etc., matching the NZTA JSON shape). Helpers `cleanText(_:)`, `formatVMSMessage(_:)`, and the `KeyedDecodingContainer` extension at the bottom (`decodeLossyString`, `decodeLossyDouble`, `decodeLossyInt`) exist because the upstream API is loose-typed (numbers as strings, missing fields, embedded display-control tokens). New decoded fields should reuse these helpers rather than calling `decode` directly. Keep this file free of `SwiftUI`/`AppKit` so the test runner can compile it standalone.
- `ViewLogic.swift` / `MapClustering.swift` — Foundation-only logic behind the views, kept out of the SwiftUI files so the tests can compile it: Flow / congestion draw order and side-by-side offsets, `AccessibleLineStyle` (width + dash per level under Differentiate Without Colour), the map pin glyphs (one per status, so no status is colour-only), `congestionListGroups` (the Auckland motorways text list in Travel Times), `timBoardListing` (Travel Times › Boards: TIM boards by region north to south, blank boards set apart), map framing, and `clusterMapPoints` / `clusterTapAction` (screen-space clustering).
- `Theme.swift` — design tokens (`Spacing`, `Radii`, and semantic `Color` extensions for the VMS palette + card stroke) and `floatingPanel(cornerRadius:)`, the Liquid Glass (`glassEffect`) background for panels floating over the map — group neighbours in a `GlassEffectContainer`; it turns solid with Reduce Transparency and gains an edge with Increase Contrast. Prefer these over scattered literals.
- `GlobalFilterToolbar.swift` — the window toolbar as a `ViewModifier`: Region and Highway (leading), the refresh status (`RefreshStatusLabel`, `.status`), Clear Filters (⌘E, also the Filtered indicator), Refresh (⌘R) and the auto-refresh menu (trailing), and Search via `.searchable(placement: .toolbar)` with `.searchFocused` (⌘F). It owns the raw Highway/Search text and the 300 ms debounce, so typing re-renders only the modifier.
- `Views.swift` — `ContentView` (a `.sidebarAdaptable` `TabView` of `Tab`s whose sidebar badges carry the section counts, the `GlobalFilterToolbar`, and per tab a `safeAreaBar(edge: .top)` holding the freshness banner and the tab's scoped filter chips; the Map floats its layer controls over the map instead), one view per `TrafficTab` (`CamerasTabView`, `RoadEventsTabView`, `VMSTabView`, `TravelTimesTabView`, `TrafficMapTabView`, `AboutView`), `SettingsView`, the `AppHelpView` shown in the secondary window, and shared chrome (`ErrorBanner`, `LoadingView`, `FilterableEmptyState` (a `ContentUnavailableView`), `Badge`, `StatCard`).

### Data flow

`ContentView` owns the single `TrafficStore` and the three filter strings (region / highway / search), then asks the store for filtered/sorted slices per tab via `filteredCameras`/`filteredEvents`/`filteredVMSSigns`. Filtering and sorting live in the store, not in the views — when extending filters, add the predicate to the shared `matches(region:highway:search:)` (the `TrafficFilterable` protocol extension in `Models.swift`) and to the relevant store accessor, and add any new input to the store's `FilterKey` so the memoized results stay correct.

- **Highway filter** matches whole highways, not substrings: `canonicalHighwayKey` maps "SH1" / "SH 1" / "State Highway 1" / "01N" / "SH1N" / "1" to the key "1" (spurs such as "1B" / "20A" stay distinct), and each model precomputes `highwayKeys` at decode time from its structured highway/journey/way fields plus "SH n" mentions in its own name/location text (not comments, detours or TIM destinations). A query that isn't a highway falls back to a whole-word match on `highwayHaystack`. Free-text search stays a substring match.
- **Road event status** is parsed into `EventStatus` (active / scheduled / resolved / unknown-raw; unknown counts as active). Only `isActiveClosure` feeds the Dock badge, the menu bar "Active closures" and the red map pins; Scheduled events show as "Upcoming"; Resolved events are hidden everywhere unless `@AppStorage("nzta.showResolvedEvents")` is on.
- **Watching filter** (`@AppStorage("nzta.filter.watchingOnly")`, the chip in the Cameras / Road Events / Travel Times bars) is applied in the store's `scoped*` accessors after the memoized slice (`watchingOnly:`), from `store.watchlist` — not in `FilterKey`.
- **TIM boards** keep their pages (`TIMSign.pages`: each page's `center` text as `header` — boilerplate such as "ESTIMATED" / "MINUTES" dropped — plus its destination/time `rows`); `lines` flattens the rows. A text-only page is a message, not a blank board.
- **EV connector status** comes from `connectorsList` (`EVConnectorSummary`: per-status counts; power, DC flag and the AC/DC/Mixed label from connectors that may work). `availability` is `.outOfService` only when none is Operative and some are Inoperative — all-Unknown means "not reported", shown normally.

The map tab (`TrafficMapTabView`) consumes the same filtered slices and renders them through a `TrafficMapLayer` enum using MapKit: muted standard style without POIs, `MapZoomStepper` / `MapCompass` / `MapScaleView`, camera bounds limited to New Zealand including the Chatham Islands (`NZMapArea`, `trafficMapCameraBounds`), and a region change frames that region's results (`mapFrame(fitting:)` in `ViewLogic.swift`; All Regions resets to the whole country). Its layer picker, counts and chips float over the map in glass panels. Pins are clustered in screen space at every zoom (`clusterMapPoints`: a world-anchored grid about one 44 pt marker wide, rounded to a power of two so small camera moves keep the same clusters and ids; reclustered in a debounced `.task(id:)` only when the pins or the grid level change). Clicking a cluster zooms in, or — for pins at the same spot or already at click-zoom's limit — lists them to pick from (`clusterTapAction`); a cluster's context menu / VoiceOver action lists them at any zoom. Coordinate parsing lives on each model as `mapCoordinate` — features without coordinates are silently dropped from the map and counted as `unmappedCount`.

### Refresh model

Refreshing belongs to the store and the App, never to a window, so it keeps running (and the menu bar and Dock badge stay current) with the main window closed.

- **Launch:** `AppController.start()` → `store.start()` marks every section loading, primes empty sections from the offline cache, then calls `loadAllData()`. `ContentView.task` only calls `store.refreshIfStale(maxAge:)` (joins the launch load; refreshes a reopened window whose data is over 2 minutes old).
- **Single flight:** `loadAllData(bustImageCache:)` runs one refresh at a time (`SingleFlight`); overlapping callers — ⌘R during an auto tick, Retry, a reconnect, the window reappearing — join it, and a joining explicit refresh "upgrades" it to fresh camera images. Each section also loads single-flight (`loadSection`), which owns that section's loading flag. Don't add a second path that fetches a section directly.
- **Sections land independently:** each section is applied the moment its own fetch completes. `isRefreshing` covers `DataSection.refreshedTogether` (cameras, events, VMS, TIM, congestion); journeys loads alongside with only its own loading flag; regions are fetch-once, and EV chargers load on the first refresh and again on a refresh once they're over an hour old (`AutoRefreshPolicy.evChargerMaxAge` — connector status changes about daily).
- **Unchanged feeds:** the JSON is sent no-store and uncompressed (no HTTP revalidation is possible), so every refresh downloads it; when a section's bytes match what's on screen (`ContentDigest`), the array isn't reassigned, its filter memo is kept and the cache file isn't rewritten.
- **Auto-refresh:** `@AppStorage("nzta.autoRefreshEnabled")` / `("nzta.refreshIntervalSeconds")` (60–600 s; `AutoRefreshPolicy`) reach `store.configureAutoRefresh` only through `AppController` — don't reschedule from views. Ticks are counted from the start of the last refresh of any kind; while the app is inactive with no window visible the interval backs off ×3 (max 15 minutes), and a refresh that fell due meanwhile runs as soon as the app is active again.
- **Failures:** a cancelled load is not an error. Offline (`NWPathMonitor`), no request is made; each section gets an offline error and keeps what it shows. Coming back online after a failure, or with saved data on screen, triggers one debounced reload. `lastUpdated` is stamped only by a successful live fetch, and the toolbar status / banner ages re-render every 30 s (`TimelineView`).
- **Camera images:** `CameraImage` (Cards.swift) loads through `URLSession.shared` / the bounded `URLCache`. When the cameras section refreshes, `cameraImageGeneration` bumps (at most every 30 s) and on-screen images re-request the same URL with `.reloadRevalidatingCacheData` — the JPEGs support ETag/304 — keeping the old frame until the new one arrives. `imageCacheToken` (`?t=`, starts at 0 so cached images survive relaunches) changes only on an explicit refresh.

### Offline cache (deliberate exception to "no caching layer")

The four primary sections (cameras / events / vms / journeys) are persisted to disk for offline use — a deliberate, documented exception to the "no caching layer" convention below. How it works:

- The fetchers in `TrafficAPIService` return a `SectionFetch` (value, data, digest) so the store gets both the decoded models **and** the raw response bytes. The store persists the **raw JSON bytes** (not re-encoded models — the models have derived stored fields and `CodingKeys` that are a strict subset, so they don't round-trip via `Encodable`). On replay the bytes go back through the same `CamerasPayload`/etc. wrappers (`decodeCached*`), preserving every derived field.
- `OfflineCache` (an `actor` in `OfflineCache.swift`) does all file IO off the main actor, writing one `<section>.json` per section under `Application Support/NZTraffic/OfflineCache/`. A write whose bytes match the file's digest only refreshes its modification date (which records when the data was last confirmed). Every operation is best-effort.
- `store.start()` primes empty sections from disk on launch (ended events are left out of a replay) before the first `loadAllData()`. On a fetch failure a section keeps what it shows, and falls back to the cached copy only if it has nothing to show; on success it overwrites both memory and disk. Saved data is tracked per section (`savedSections`, `savedDates`).
- `store.freshnessBanner` drives the `OfflineBanner` above each tab's content: *offline*, *couldn't reach NZTA* (only when a live fetch actually failed), or a neutral *showing saved data … updating…* while a launch's live load runs — always dated by the **oldest** data shown. The Dock badge gets a "?" and the menu bar says "(saved data)" when the closure count comes from saved or failed events.
- Escape hatches: Settings › Clear Offline Cache (and Help › Clear Offline Cache…) deletes the files and the image `URLCache`, then reloads. `LaunchGuard` discards the saved copy at launch if the previous launch died before its first refresh finished, so saved data that crashes the app on display can't loop.

## Conventions worth knowing

- The NZTA API is the only data source. There is no proxy and no auth. The **one** persistence exception is the offline cache described under "Refresh model" above (raw section JSON in Application Support); don't add other caching layers without reason.
- VMS message strings arrive with embedded display-control tokens; always run them through `formatVMSMessage` before showing.
- String/number fields from the API can be either type or absent — go through `decodeLossyString` / `decodeLossyDouble` and `cleanText`, not the raw `decode` calls.
- Errors are per-section by design (`store.errors[.cameras]` etc.) and rendered via `ErrorBanner` inside each tab. A failed fetch records the error but **keeps the section's last-known-good data** (it no longer zeroes the array), so other sections — and stale data — stay intact.
- Camera image URLs are suffixed with `?t=\(store.imageCacheToken)`; the token only changes on an explicit refresh. Auto-refresh instead bumps `store.cameraImageGeneration`, and `CameraImage` revalidates the unchanged URL (ETag/304) rather than re-downloading every image. Only the camera JPEGs revalidate — the traffic JSON is `no-store`.
- New decoded fields and parsing logic should get a case in `Tests/ModelTests.swift`; run `./run_tests.sh` before committing model changes.
